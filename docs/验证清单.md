# dsh-forget-session 验证 / 排障清单

## 用法（两段式确认）

1. 会话行「…」菜单 → 点 **「遗忘会话」**（官方四项之后的那一项）
2. 该行变成 **「再次点击确认遗忘」**（此时再点才真正执行）
3. 再点一次 → 行消失，会话与其磁盘数据被移除；顶部 Toast 汇报删除摘要
4. 之后约 2 分钟内 Host 的**复活守卫**自动复查若干次：被活体 teardown 迟到
   写入重建的目录、或 Windows 句柄残留的目录，都会被自动补删

不想删就点别处关掉菜单即可，不会有任何副作用。

## 会话行为什么会真正消失（机制）

侧栏分组的官方算法：

```
accounted = 所有 workspace.sessionIds 的并集
未分组    = 客户端会话列表里的 id − accounted
```

v2.2 起，Host 端先把活体会话从 `SessionStore` 摘除（entry 自带的官方
`detach()`：`store.delete` + `attachments.delete` + `emitDisposed`）——
这会触发服务端 `api-session/removed` 帧，`session.list` 也不再列出它；
随后客户端半再调用官方 `sessions.handleSessionRemoved(id)` +
`sessions.refresh()` 重拉基线，双保险让行立刻、且持续地消失。

## 「未分组」幽灵的三个来源

1. **Windows 活体删除竞态**：会话打开过就有 write handle / 跨进程 lease，
   `rm` 报 EBUSY 静默失败 → 文件残留 → 重启后回到「未分组」。v2 删除后
   验证性复查 + 退避重试 + ~130s 复活守卫，句柄释放后或迟到写入重建后
   都会自动补删。
2. **客户端列表复活**：Host 的 session.list 仍列出活体会话，客户端重连触发
   的 refreshList 会把已删行合并回来。v2 删除后主动 `sessions.refresh()`。
3. **活体从未摘除（v2.2 根治）**：`SessionStore` 没有公开 remove API，
   会话进过 store 后 `session.list`（活体+持久化合并）永远列出它 ——
   删除后**立刻**回到「未分组」；且持久层 writer 握着 write handle 顶住
   磁盘，`rm` EBUSY，守卫删 ~130s 也是白删。v2.2 走 `entry.detach()`
   官方通道摘活体：行从列表消失（官方 removed 帧）+ write handle 释放
   （删盘才真正删得动）。

> 历史上还有个「空壳清扫从未生效」的老问题（v1 的清扫方法引用了未导入的
> `zlib`）。那个能力连同「会话体检」菜单已按用户要求整体移除 —— 现在契约面
> 只有 `delete` 一个方法，不再有会报 `typert gateway` 错误的多余入口。

## 重启后自检

- 菜单里能看到「遗忘会话」 → 客户端半已加载
- 点第一次会变成「再次点击确认遗忘」 → 交互链正常
- 点第二次后行消失、且**不出现**「未分组」 → 修复生效
- 删除后等 30 秒再刷新/重连 → 行不再回来（复活守卫生效）
- 菜单里**没有**别的多余项（如「会话体检」） → 契约面已收干净

## 若出现异常

错误**直接显示在菜单行上**（不静默）：

| 行上显示 | 含义 | 处理 |
|---|---|---|
| `遗忘失败：Host 服务未连接（restart DSH）` | 宿主半没加载 | 重启 DSH |
| `遗忘失败：workspaceRegistry service is unavailable` | workspace 插件未就绪 | 重启 DSH |
| `file still present after retries`（控制台警告） | Windows 句柄残留 | 无需处理 —— 复活守卫会在句柄释放后自动补删 |

## 恢复点

删除前会先走官方「停止并归档」通道再摘记账。即使中途失败，会话最坏情况
是**「已归档」**，可在侧栏「全部对话（显示已归档）」找回（此路径下磁盘
文件仍在）。

## 记忆完整性

灵枢记忆走 `session/event` 事件流、数据在 `~/.dsh/.dsh-memory`，
与会话日志/投影缓存文件不相交，遗忘会话不影响已沉淀的记忆。
